## How DeepWiki is organized

DeepWiki pages go from abstract to concrete, and each page follows the same pattern:

1. **Overview**: what it is, why it exists, a one-paragraph mental model.
2. **Architecture**: how the pieces fit together, with a Mermaid diagram.
3. **Subsystems**: one page per feature, each explaining how it works and pointing at the exact files.
4. **How-to / reference**: tasks (add a host, rotate a secret) and lookup tables (options, keybinds).

Each page opens with a short summary and a list of "relevant source files". Pages are heavy on tables, diagrams, and links to real paths. That is what makes them feel trustworthy: every claim points at code.

## Suggested layout for your repo

```
README.md                 # storefront: pitch, screenshots/video, features, links
docs/
├── README.md             # index / table of contents (optional but useful)
├── philosophy.md         # why: declarative, reproducible, ephemeral root, CLI-first
├── installation.md       # from a live ISO: disko → sops key → nixos-install
├── architecture.md       # flake inputs, hosts/ vs modules/ vs home/, data flow
├── hosts.md              # laptop vs Raspberry Pi: what each imports and why
├── disks-and-impermanence.md   # disko layout, btrfs rollback, what's in /persist
├── secrets.md            # sops-nix + age: key location, adding/rotating secrets
├── theming.md            # variables.nix, Stylix, matugen, specialisation toggle
├── desktop.md            # Hyprland, waybar, rofi... + keybinds table
├── terminal.md           # zsh, tmux, vim/nixvim, CLI tools
├── services.md           # Pi services (as they land)
├── usage.md              # daily workflow: rebuild, update, theme-toggle, rollback
├── troubleshooting.md    # known pitfalls and fixes
└── assets/               # images, diagrams
```

You'd split it this way for three reasons:

- **Split by question, not by directory.** Each file answers one question: "why?", "how do I install?", "how does X work?", "how do I do Y?". Mirroring the `modules/` tree one-to-one gives you docs that rot as you refactor.
- **Pick one reader per page.** `installation.md` is for future-you on a blank disk at 2am, so keep it a numbered, copy-pasteable procedure. `architecture.md` is for someone reading to understand, so use prose and diagrams.
- **Keep each page to one screen of scrolling or two.** If a page needs more, split it (`secrets.md` and `impermanence.md` are better separate than merged).

## Anatomy of each page

````md
# Secrets (sops-nix)

> One-sentence summary of what this covers and why it matters.

**Source files:** [`modules/system/sops.nix`](../modules/system/sops.nix), [`.sops.yaml`](../.sops.yaml)

## Overview
Mental model in 3–5 lines.

## How it works
Mermaid diagram or table, then explanation.

## Common tasks
### Add a secret
### Rotate the age key

## Gotchas
````

Some conventions that pay off:

- **Mermaid for flows.** GitHub renders it natively, e.g. the boot flow: *initrd → rollback btrfs root → mount /persist → activate*.
- **Tables for lookups.** Examples are host vs modules, keybind vs action, and path vs why it's persisted.
- **Relative links to code**, so docs and source stay navigable on GitHub.
- **Task-oriented headings** ("Add a new host") rather than noun headings ("Hosts").
- **Document decisions** ("why Stylix + specialisation instead of a rebuild"), since that's what you'll forget.
- **Keep commands copy-pasteable**, with no `$` prompts and no placeholders you can't spot.

## The README

Keep it short, with five parts:

- A one-line pitch.
- A screenshot or video, ideally a short GIF/MP4 of the theme toggle or desktop.
- A bullet **Features** list where each bullet links to a doc (Declarative disks via disko, Ephemeral root, Encrypted secrets, Runtime light/dark switching...).
- A quick start of three commands.
- A "Documentation" link list to `docs/*`.

Since the repo is public, the README is what visitors see, so put the visuals there and keep the depth in `docs/`.

## Workflow tip

Write `architecture.md` and `installation.md` first, since they're the highest value. Then test `installation.md` by actually following it on a VM or spare disk. Anything you have to improvise belongs in the doc. You can also ask Claude Code to draft each page from the relevant source files, then review it. It's good at the "Source files" lists and Mermaid diagrams, but you need to verify the rationale sections.
